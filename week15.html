一、雲端運算基礎

1.1 什麼是雲端運算？

雲端運算是一種透過網際網路提供運算資源（伺服器、儲存、資料庫、網路、軟體等）的模式，使用者可以按需使用，按使用量付費。

雲端運算的五大特性（NIST 定義）

  • 按需自助服務（On-demand Self-service）：使用者可以自行配置資源，無需人工介入
  • 廣泛的網路存取（Broad Network Access）：透過標準機制從各種裝置存取
  • 資源池（Resource Pooling）：供應商的資源集中管理，動態分配給多個使用者
  • 快速彈性（Rapid Elasticity）：可以快速擴展或縮減資源
  • 可測量的服務（Measured Service）：資源使用可以監控、控制和報告

1.2 雲端服務模型

1.3 雲端部署模型

四種部署模型

  • 公有雲（Public Cloud）：
    • 向公眾開放
    • 共享基礎設施
    • 成本較低
    • 範例：AWS、Azure、GCP
  • 私有雲（Private Cloud）：
    • 專屬於單一組織
    • 更好的控制與安全性
    • 成本較高
    • 範例：OpenStack、VMware vCloud
  • 混合雲（Hybrid Cloud）：
    • 結合公有雲與私有雲
    • 資料與應用可在兩者間移動
    • 靈活性高
  • 社群雲（Community Cloud）：
    • 由具有共同需求的組織共享
    • 介於公有雲與私有雲之間

二、容器編排與 Kubernetes

2.1 為什麼需要容器編排？

當容器數量增加到數十、數百甚至數千個時，手動管理變得不切實際。容器編排工具自動化容器的部署、擴展、網路和管理。

容器編排解決的問題
  • 自動化部署與更新
  • 服務發現與負載平衡
  • 自動擴展（Scaling）
  • 自我修復（Self-healing）
  • 配置管理
  • 儲存編排

2.2 Kubernetes 基礎

Kubernetes（K8s）是目前最流行的容器編排平台，由 Google 開發並開源。

Kubernetes 核心概念

  • Pod：最小部署單位，包含一個或多個容器
  • Node：工作節點，執行 Pod 的機器
  • Cluster：由多個 Node 組成的集群
  • Deployment：管理 Pod 的宣告式更新
  • Service：提供網路存取 Pod 的抽象層
  • Namespace：虛擬集群，用於資源隔離
  • ConfigMap & Secret：配置與敏感資料管理
Kubernetes 架構： Master Node (Control Plane): ┌────────────────────────────────────┐ │ API Server │ Scheduler │ │ Controller │ etcd (資料庫) │ └────────────────────────────────────┘ │ ┌───────┴───────┐ │ │ Worker Node 1 Worker Node 2 ┌──────────┐ ┌──────────┐ │ kubelet │ │ kubelet │ │ kube-proxy│ │ kube-proxy│ │ │ │ │ │ ┌──Pod──┐│ │ ┌──Pod──┐│ │ │ App ││ │ │ App ││ │ └──────┘│ │ └──────┘│ └──────────┘ └──────────┘

2.3 Kubernetes 核心功能

自動擴展（Auto-scaling）

  • Horizontal Pod Autoscaler（HPA）：根據 CPU/記憶體使用率自動調整 Pod 數量
  • Vertical Pod Autoscaler（VPA）：調整 Pod 的資源請求
  • Cluster Autoscaler：調整集群節點數量

滾動更新（Rolling Update）

逐步更新 Pod，確保服務不中斷。

自我修復（Self-healing）

  • 重啟失敗的容器
  • 替換無回應的 Pod
  • 健康檢查（Liveness & Readiness Probes）

三、微服務架構

3.1 微服務 vs 單體架構

特性 單體架構（Monolithic） 微服務架構（Microservices）
結構 所有功能在單一應用 多個獨立的小服務
部署 整體部署 獨立部署
擴展 垂直擴展 水平擴展
技術棧 統一技術棧 可使用不同技術
開發速度 初期快，後期慢 持續快速迭代
複雜度 較低 較高
適用場景 小型應用、MVP 大型、複雜系統

3.2 微服務設計原則

核心原則

  • 單一職責：每個服務專注於一個業務功能
  • 自治性：服務可獨立開發、部署、擴展
  • 去中心化：避免單點故障
  • 彈性設計：容錯與降級機制
  • 可觀測性：日誌、監控、追蹤
  • API 優先：明確的服務介面

3.3 微服務挑戰

常見挑戰
  • 分散式系統複雜性：網路延遲、部分失效
  • 資料一致性：分散式交易處理困難
  • 服務間通訊：增加網路開銷
  • 測試複雜度：整合測試困難
  • 部署協調：需要自動化工具
  • 監控與除錯：跨服務追蹤困難

四、Serverless 運算

4.1 什麼是 Serverless？

Serverless 不是沒有伺服器，而是開發者不需要管理伺服器。雲端供應商負責基礎設施管理，開發者只需關注程式碼。

Serverless 的特點

  • 事件驅動：由事件觸發執行
  • 自動擴展：根據需求自動調整資源
  • 按使用付費：只為實際執行時間付費
  • 無狀態：函數不保存狀態
  • 快速部署：專注於業務邏輯

4.2 Function as a Service (FaaS)

FaaS 是 Serverless 的核心，允許開發者上傳函數程式碼，由事件觸發執行。

平台 服務名稱 支援語言
AWS Lambda Node.js, Python, Java, Go, C#, Ruby
Azure Functions C#, JavaScript, Python, Java, PowerShell
Google Cloud Cloud Functions Node.js, Python, Go, Java

4.3 Serverless 應用場景

  • Web API 與後端服務
  • 資料處理與 ETL
  • 即時檔案處理（圖片縮放、影片轉碼）
  • 定時任務（Cron jobs）
  • 聊天機器人
  • IoT 資料處理

五、現代作業系統趨勢

5.1 作業系統的演進

發展趨勢

  • 雲端原生（Cloud-Native）：

將運算能力從雲端推向網路邊緣，靠近資料來源。

邊緣運算的優勢
  • 降低延遲
  • 減少頻寬使用
  • 提高隱私與安全

  • 即時決策

6.3 ConfigMap 與 Secret

config.yaml 配置管理 
# ConfigMap - 一般配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  database_host: "mysql.default.svc.cluster.local"
  database_port: "3306"
  log_level: "info"
---
# Secret - 敏感資料
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
data:
  # Base64 編碼
  database_user: dXNlcm5hbWU=  # username
  database_password: cGFzc3dvcmQ=  # password
---
# 使用 ConfigMap 和 Secret 的 Pod
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:latest
    env:
    # 從 ConfigMap 取得
    - name: DB_HOST
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: database_host
    # 從 Secret 取得
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: app-secret
          key: database_password

  maxReplicas: 10

  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70  # CPU 使用率超過 70% 就擴展
  - type: Resource

6.5 微服務範例（Python Flask）

microservice.py 簡易微服務 
from flask import Flask, jsonify
import requests
import os

app = Flask(__name__)

SERVICE_NAME = os.getenv('SERVICE_NAME', 'unknown')
PORT = int(os.getenv('PORT', 5000))

@app.route('/health')
def health():
    return jsonify({
        'status': 'healthy',
        'service': SERVICE_NAME
    })

@app.route('/api/info')
def info():
    return jsonify({
        'service': SERVICE_NAME,
        'version': '1.0.0',
        'port': PORT
    })

@app.route('/api/call-other')
def call_other():
    # 呼叫另一個微服務
    try:
        other_service = os.getenv('OTHER_SERVICE_URL')
        response = requests.get(f'{other_service}/api/info', timeout=5)
        return jsonify({
            'this_service': SERVICE_NAME,
            'other_service_response': response.json()
        })
    except Exception as e:
        return jsonify({
            'error': str(e)
        }), 500

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=PORT)

7. 問答題：比較 IaaS、PaaS 和 SaaS，並說明各自適用的場景

參考答案：IaaS（基礎設施即服務）提供虛擬化資源，使用者控制 OS 和應用程式，適合需要完全控制環境的情況，如自建系統、特殊配置需求。PaaS（平台即服務）提供開發平台，使用者只需部署應用程式，適合快速開發、不想管理基礎設施的團隊。SaaS（軟體即服務）提供完整應用程式，使用者直接使用，適合標準化需求，如郵件、協作工具。選擇考量：控制需求、技術能力、開發速度、成本。IaaS 靈活但複雜，SaaS 簡單但客製化受限，PaaS 介於兩者之間。

8. 問答題：解釋為什麼微服務架構適合大型應用，並說明實施時需要注意的關鍵點

參考答案：微服務適合大型應用的原因：(1) 團隊可獨立開發不同服務，提高開發效率；(2) 服務可獨立部署和擴展，不影響整體系統；(3) 故障隔離，一個服務出錯不會拖垮整個系統；(4) 技術多樣性，可為不同服務選擇最適合的技術。關鍵注意點：(1) 服務劃分要合理，避免過度拆分；(2) 需要完善的監控和追蹤系統；(3) API 設計要穩定；(4) 資料一致性處理（分散式交易）；(5) 服務間通訊的效能和可靠性；(6) 需要強大的 DevOps 能力和自動化工具；(7) 初期投入較大，不適合小型項目。
